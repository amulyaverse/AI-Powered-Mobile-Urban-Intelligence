==================================================

1. UNIFIED PERSISTENT EVENT ID
   ==================================================

PROBLEM:

The system currently generates UUIDs inside the pothole/healing cache, but the emitted pothole detection events do not contain that identifier.

A typical detection event currently contains fields equivalent to:

event_type
confidence
severity
bus_id
camera_id
timestamp
latitude
longitude

but does NOT contain event_id.

This breaks the relationship between:

physical pothole
↓
persistent pothole record
↓
detection event
↓
treatment/resolution event

FIX:

Introduce a persistent identifier for every newly registered physical pothole.

Use the repository's existing UUID mechanism if appropriate rather than inventing a new ID technology.

The ID must:

- be generated exactly once when a genuinely new pothole is registered;
- be non-empty;
- be unique among active/persistent potholes;
- remain unchanged when the pothole is detected repeatedly;
- survive JSON serialization/deserialization;
- survive application restart;
- be associated with the same pothole's future resolution/treatment event.

A detection of an already-known pothole MUST NOT generate a new event_id.

Make the event structure include the identifier using the repository's naming convention, preferably:

"event_id"

unless the existing architecture strongly dictates another name.

Example:

First detection:

{
"event_id": "abc-123",
"event_type": "pothole",
...
"latitude": 28.6139,
"longitude": 77.2090
}

Repeated detection of the same physical pothole must continue referring to:

"event_id": "abc-123"

Do NOT generate:

abc-123
def-456
ghi-789

for the same physical pothole merely because it was detected in different frames.

3. CONFIGURABLE DUPLICATE-DETECTION RADIUS

PROBLEM:

The current duplicate-detection logic uses a hard-coded approximately 2 metre threshold even though the system has configurable geographic parameters.

This makes the behavior inconsistent with the requested configurable GPS tolerance.

FIX:

Introduce a clearly named configurable deduplication radius.

For example:

DEDUPLICATION_RADIUS_METERS

or an equivalent configuration field consistent with the existing configuration architecture.

Do NOT hard-code the threshold inside the duplicate-detection function.

Use geographic distance rather than exact floating-point coordinate equality.

The behavior must be:

distance <= configured duplicate radius
→ same physical pothole

distance > configured duplicate radius
→ different pothole

Use the repository's existing Haversine implementation if appropriate.

Keep the healing/repaired threshold logically separate from the duplicate-detection threshold.

Do NOT accidentally use the treatment/healing radius as the deduplication radius unless the repository's architecture explicitly intends that.

==================================================
4. SAME-LOCATION DETECTION

Repeated detections such as:

28.613900, 77.209000
28.613905, 77.209005
28.613910, 77.209010

must resolve to the same persistent pothole when they fall within the configured deduplication radius.

The system should:

1. find the existing pothole;
2. reuse its event_id;
3. avoid creating another permanent pothole record.

Do not rely on exact coordinate equality.

At the same time, geographically separated potholes must remain independent.

Example:

A:
28.613900, 77.209000

B:
28.620000, 77.220000

must result in two independent pothole records and two unique IDs.

6. DUPLICATE EVENT/CACHE ID PROTECTION

PROBLEM:

Loading duplicate IDs into a dictionary/cache can silently overwrite an unrelated pothole.

For example:

[
{
"id": "DUP",
"latitude": 28.6139,
"longitude": 77.2090
},
{
"id": "DUP",
"latitude": 28.6200,
"longitude": 77.2200
}
]

must NOT silently discard one record.

FIX:

Validate persistent records when loading.

If duplicate IDs are found:

- raise a clear error, OR
- perform a documented safe migration/recovery strategy.

Do NOT silently overwrite records.

The safest default for corrupted persistent state is generally to fail clearly rather than destroy data.
